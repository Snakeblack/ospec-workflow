# VS Code Agent Plugin Installation

This repository installs as a VS Code Agent Plugin. It is not a VS Code extension flow.

Agent Plugins are in preview. Before installing, review the plugin contents because it may include hooks and MCP servers that execute code locally.

## What this plugin provides

The repository keeps two manifests in sync: `.plugin.json` is the canonical manifest for VS Code/direct-load and `.claude-plugin/plugin.json` preserves the shape expected by the generated Claude distribution (and is the source read by the generator). Always edit the canonical one first; both must match and `scripts/manifest-sync.test.js` verifies this in CI.

| Area | Source | What it provides |
| --- | --- | --- |
| Agents | `agents/` | SDD orchestration and phase agents. |
| Prompt files | `commands/*.prompt.md` | User-visible prompt files, such as `/sdd-new`, `/sdd-apply`, and `/sdd-verify`. |
| Skills | `skills/` | Reusable rules for SDD phases, reviews, commits, documentation, and related flows. |
| Instructions | `rules/` | Instruction files bundled with the plugin and generated by the VS Code plugin creation flow. |
| MCP servers | `.mcp.json` | Configuration of the MCP servers: Context7 (library docs, uses `CONTEXT7_API_KEY`) and MarkItDown (document conversion). |
| Hooks | `hooks/hooks.json` and `scripts/hooks/` | Local Node.js scripts for session persistence, tool-use validation, and OpenSpec artifact checks. |

The `.github/instructions/` directory is only a workspace mirror for instruction files. The rules bundled with the plugin live in `rules/`.

## How to install from source

Use this path when you want VS Code to manage the plugin from a source repository.

1. Open a VS Code build that supports the Agent Plugins preview.
2. Open the Agent Plugins installation flow.
3. Choose the option to install from a Git repository URL.
4. Enter this project's repository URL.
5. Review the plugin manifest, hooks, MCP server configuration, and scripts before accepting the installation.
6. Enable the plugin when VS Code asks.
7. Reload VS Code if the plugin does not appear right away.

Trust checklist before accepting:

- Confirm that `.plugin.json` and `.claude-plugin/plugin.json` point only to the expected plugin assets.
- Review `hooks/hooks.json` because it starts local Node.js scripts.
- Review `scripts/hooks/` because those scripts run on hook events.
- Review `.mcp.json` because it may start local processes for MCP servers.
- Confirm you are comfortable providing `CONTEXT7_API_KEY` when you need MCP access.

Plugin support may be disabled by organization policy. If the Agent Plugins UI or settings do not appear, check your VS Code version and the configuration managed by your organization.

## How to enable it locally with `chat.pluginLocations`

Use this path when you are developing or testing this repository directly from disk in VS Code. It supports two modes:

### Option A: Without model routing (direct use of the source)
1. Clone the repository locally.
2. Open the VS Code settings in JSON format.
3. Add the root of this repository to `chat.pluginLocations`.
4. Reload VS Code.

### Option B: With `models.yaml` model routing (Recommended)
1. Clone the repository locally.
2. Run the automatic setup script for VS Code:
   ```powershell
   npm run setup:vscode
   ```
   *(This builds the VS Code target into `dist/vscode` and automatically adds it to `chat.pluginLocations` in your settings).*
3. If you make code changes and want to reload the plugin, run:
   ```powershell
   npm run reload:vscode
   ```
4. Reload VS Code.

In both cases, open the Agent Plugins view and confirm that `ospec-workflow` is enabled.

Minimal `settings.json` example:

```json
{
  "chat.pluginLocations": [
    "C:\\dev\\Hiberus\\ospec-workflow"
  ]
}
```

If you keep the repository at another path, replace the value with the local path of your clone.


## Generating for other targets with configure

The repository uses VS Code Agent Plugin as the canonical format. The `vscode` target is identity: VS Code can load the repository directly, without generating `dist/`. For Claude Code and GitHub Copilot CLI, the generator produces native trees under `dist/` without modifying the source.

```powershell
# Claude Code: temporary session load
node scripts/configure/cli.js --target claude --out dist/claude

# Claude Code: persistent installation with local marketplace
node scripts/configure/claude-marketplace.js

# Codex CLI (local build)
node scripts/configure/cli.js --target codex --out dist/codex

# Codex CLI (global installation)
npm run setup:codex

# GitHub Copilot CLI (local build)
node scripts/configure/cli.js --target github-copilot --out dist/github-copilot

# GitHub Copilot CLI (global installation)
npm run setup:copilot

# opencode (local build)
node scripts/configure/cli.js --target opencode --out dist/opencode

# opencode (global installation)
npm run setup:opencode

# Cursor IDE (local build)
npm run build:cursor
# equivalent: node scripts/configure/cli.js --target cursor --out dist/cursor

# Cursor IDE (global installation in ~/.cursor)
npm run setup:cursor

# Skip validation for quick inspection
node scripts/configure/cli.js --target claude --out dist/claude --no-validate
```

| Target | Output | Validation |
| --- | --- | --- |
| `vscode` | Direct load of the source repository with `.plugin.json`; generates no output. | `node scripts/check.js` |
| `claude` | Renames `*.agent.md`/`*.prompt.md` to `*.md`, restructures the manifest and the hooks, substitutes tool names, rewrites command variables (`${input}` -> `$ARGUMENTS`; `${input:name}` -> `$name` + `arguments:`), bundles `rules/`, and emits the orchestrator as a **skill** (`skills/sdd-orchestrator/SKILL.md`). Generates `dist/claude/`, meant for temporary loading with `claude --plugin-dir`. | `claude plugin validate --strict dist/claude` |
| `claude-marketplace` | Wraps the Claude tree into an installable local marketplace. Generates `dist/claude-marketplace/.claude-plugin/marketplace.json` and places the plugin in `dist/claude-marketplace/plugins/ospec-workflow/`. | `claude plugin validate dist/claude-marketplace` and `claude plugin validate --strict dist/claude-marketplace/plugins/ospec-workflow` |
| `codex` | Generates `agent.md`, `.codex/agents/*.toml`, `skills/`, runtime `scripts/`, and a native `hooks.json`. `setup:codex` installs them globally without using plugins or marketplace. | `scripts/configure/validate-codex.js`, executed by profile validation and by `node scripts/check.js`. |
| `github-copilot` | Generates a `.github/` layout with instructions, prompts, chatmodes, MCP, and hook runtime for GitHub Copilot CLI / coding agent. | `scripts/configure/validate-github-copilot.js`, executed by profile validation and by `node scripts/check.js`. |
| `opencode` | Generates a `.opencode/` layout (`agents/`, `commands/`, `instructions/`, `plugins/ospec.js`) plus `opencode.json` (schema + `mcp` + `instructions`) for opencode. Renames the main agent `sdd-orchestrator` to `ospec-workflow` for native display. No shell hooks: the runtime is bridged with a JS plugin. | `scripts/configure/validate-opencode.js`, executed by profile validation and by `node scripts/check.js`. |
| `cursor` | Generates `agents/*.md`, `commands/*.md`, `rules/*.mdc` (incl. `agents-protocol.mdc` from `AGENTS.md`), camelCase `hooks.json`, and runtime. `build:cursor` / `setup:cursor` are the supported flow: generates `dist/cursor/` and syncs it into `~/.cursor` expanding `__OSPEC_CURSOR_ROOT__`. | `scripts/configure/validate-cursor.js`, executed by profile validation and by `node scripts/check.js`. |

Each generated tree is **self-contained**: the generator follows the `require` calls from the hooks and includes their runtime (`scripts/hooks/` plus its `scripts/lib/` dependencies), without tests and without the generator itself.

Recommended local validation before publishing changes:

```powershell
node scripts/check.js
```

In Claude Code there are two different outputs:

- `dist/claude`: used for temporary loading with `--plugin-dir`.
- `dist/claude-marketplace`: wraps the Claude plugin in a local marketplace for persistent installation across sessions.

## Installing the generated tree per tool

- **VS Code**: use the repository directly (`chat.pluginLocations`), without generating.
- **Claude Code temporary**: generate `dist/claude/` and load it with `claude --plugin-dir dist/claude`. This path applies only to the current session.
- **Claude Code persistent**: generate `dist/claude-marketplace/`, register that local marketplace and then install `ospec-workflow@ospec-tools`.
- **GitHub Copilot CLI (Local/Project)**: generate `dist/github-copilot/` and copy its contents (`.github/`, `.mcp.json`, and `scripts/`) into the destination repo root.
- **GitHub Copilot CLI (Global)**: builds, copies, and registers all agents, prompts, instructions, hooks, and skills in the user's global directory (`~/.copilot/`), merging the MCP configuration into `mcp-config.json` automatically and permanently for any project.
- **Codex CLI (Global)**: builds `dist/codex/`, installs `AGENTS.md`, agents, skills, and runtime into `~/.codex/`, merges its native hooks into `~/.codex/hooks.json` and reuses equivalent MCPs or adds only the missing ones via `codex mcp`.
- **Codex CLI (Local/Project)**: `npm run install:codex -- ../my-project` copies only `.codex/agents/*.toml` to `<repo>/.codex/agents/`; it preserves any existing `config.toml` and does not copy `.codex-plugin/plugin.json` into the destination repo.
- **opencode (Local/Project)**: generate `dist/opencode/` and copy its contents (`.opencode/`, `opencode.json`, `skills/`, and `scripts/`) into the destination repo root. opencode discovers agents/commands/instructions under `.opencode/` and reads `opencode.json` (MCP + instructions); the `.opencode/plugins/ospec.js` plugin bridges the hooks runtime.
- **opencode (Global)**: builds, copies, and registers all agents, commands, instructions, and plugins in the user's global directory (`~/.config/opencode/`), merging the MCP configuration into `opencode.json` automatically and permanently for any project. In both opencode cases, the main agent is renamed to `ospec-workflow`.
- **Cursor IDE (Global)**: `npm run build:cursor` generates `dist/cursor/`; `npm run setup:cursor` validates and syncs that tree into `~/.cursor`, expanding `__OSPEC_CURSOR_ROOT__` in `hooks.json` to the absolute path (quoted only if `$HOME` contains spaces) and copying the `ospec-hooks` binary to the managed runtime.

#### Native global installation

```powershell
npm run setup:codex
```

This installer:
1. Builds and validates `dist/codex/`.
2. Copies the self-contained runtime to `~/.codex/ospec-workflow/` and syncs the agent skills into `~/.agents/skills/` by content.
3. Merges the five OSpec events into `~/.codex/hooks.json`, preserving unrelated hooks.
4. Runs `codex mcp list --json`; deduplicates by `command` + `args`, keeps name collisions, and adds only the missing servers with valid IDs.
5. Does not install or register a Codex plugin or marketplace.

#### Per-repository local installation

```powershell
npm run install:codex -- ../my-project
```

This variant writes only:

```text
<repo>/.codex/agents/*.toml
```

Without additional flags, the installer does not create or modify `.codex/config.toml`. If Codex rejects the exact legacy key `service_tier = "default"`, the global installation offers an explicit repair:

```powershell
npm run setup:codex:repair
```

On Windows PowerShell, this dedicated script avoids relying on npm flag forwarding. If you need to invoke the installer directly, use `node scripts/configure/install-codex.js --repair-config`; to preview without writing, use `node scripts/configure/install-codex.js --dry-run --repair-config`.

The repair removes only that top-level assignment, preserves BOM, line breaks, comments, and the mode of the rest of the file, and creates a unique byte-for-byte backup. The write is published transactionally and validated with the Codex CLI; on a write, rename, or validation failure, it rolls back to the original and preserves recoverable evidence. Other unsupported keys remain intact and produce a diagnostic. `auth.json`, other keys, and user-owned MCPs stay out of scope. The local variant with `<repo>` rejects the flag and never mutates global configuration.

### Claude Code: persistent installation with a local marketplace

Use this path when you want Claude Code to remember the plugin across sessions.

First generate the local marketplace:

```powershell
node scripts/configure/claude-marketplace.js
```

Validate the marketplace and the included plugin:

```powershell
claude plugin validate dist/claude-marketplace
claude plugin validate --strict dist/claude-marketplace/plugins/ospec-workflow
```

Add the marketplace with an explicit local path:

```powershell
$marketplace = (Resolve-Path ".\dist\claude-marketplace").ProviderPath
claude plugin marketplace add "$marketplace" --scope user
```

Install the plugin from that marketplace:

```powershell
claude plugin install ospec-workflow@ospec-tools
```

Open Claude Code normally:

```powershell
claude
```

Verify inside the session:

```text
/plugin
/reload-plugins
```

Expected result:

- The `ospec-tools` marketplace appears registered.
- The `ospec-workflow@ospec-tools` plugin appears installed and enabled.
- The SDD commands and the orchestrator skill are available without using `--plugin-dir`.

#### Note for PowerShell

Do not use this form:

```powershell
claude plugin marketplace add dist/claude-marketplace --scope user
```

On Windows/PowerShell it may be interpreted as a Git/GitHub origin instead of a local path, causing SSH clone errors such as:

```text
Failed to clone marketplace repository
SSH host key is not in your known_hosts file
```

Use an explicit local path:

```powershell
claude plugin marketplace add .\dist\claude-marketplace --scope user
```

Or, preferably:

```powershell
$marketplace = (Resolve-Path ".\dist\claude-marketplace").ProviderPath
claude plugin marketplace add "$marketplace" --scope user
```

The expected structure of the generated marketplace is:

```text
dist/claude-marketplace/
  .claude-plugin/
    marketplace.json
  plugins/
    ospec-workflow/
      .claude-plugin/
        plugin.json
      agents/
      commands/
      skills/
      hooks/
      scripts/
      .mcp.json
```

### GitHub Copilot CLI / coding agent

The `github-copilot` target supports two installation modes: local (per project) and global (for the user's whole machine).

#### Local installation (per project)

Generate the native tree:

```powershell
node scripts/configure/cli.js --target github-copilot --out dist/github-copilot
```

Copy the generated content into the destination repository root:

```text
dist/github-copilot/
  .github/
  .mcp.json
  scripts/
```

Or use the direct targets installer:

```powershell
npm run install:copilot -- ../my-project
```

Verify that the generated `.github/` files land at the destination repo root and that the hook scripts travel together with the required runtime.

#### Global installation (for any project)

Install the plugin permanently at user level:

```powershell
npm run setup:copilot
```

*(If you make modifications and need to update the global installation, you can rerun `npm run reload:copilot` or `npm run setup:copilot` interchangeably).*

This idempotent installer performs the following steps:
1. Builds the `github-copilot` target into `dist/github-copilot/`.
2. Copies the compiler hook binary `ospec-hooks` appropriate for the architecture into `scripts/hooks/` (if present).
3. Copies all generated folders (`agents/`, `prompts/`, `instructions/`, `hooks/`, `skills/`, and `scripts/`) to the global Copilot CLI configuration directory:
   - **Windows**: `C:\Users\<User>\.copilot\`
   - **Linux/macOS**: `~/.copilot/`
4. Dynamically merges the MCP server configurations from `.mcp.json` with Copilot's global `mcp-config.json`.

### Codex CLI

The `codex` target allows two installation modes: local (per project) and global (for the user's whole machine).

#### Local installation (per project)

Build and sync the TOML agents directly into the root of your destination project:

```powershell
npm run install:codex -- ../my-project
```

This will copy the TOML agents into `.codex/agents/` and does not modify the project's `.codex/config.toml`.

#### Global installation (for any project)

Install the native Codex configuration permanently at user level:

```powershell
npm run setup:codex
```

*(To update it, run `npm run setup:codex` again.)*

This idempotent installer performs the following steps:
1. Builds the `codex` target into `dist/codex/`.
2. Copies `AGENTS.md`, all TOML agents, the skills, and the hooks runtime to the global Codex directory:
   - **Windows**: `C:\Users\<User>\.codex\agents\`
   - **Linux/macOS**: `~/.codex/agents/`
3. Merges the OSpec native hooks into `~/.codex/hooks.json` without overwriting unrelated hooks.
4. Registers Context7 and MarkItDown only once via the native Codex CLI, without overwriting pre-existing entries.
5. Does not install or register Codex plugins or marketplaces.

### opencode

The `opencode` target allows two installation modes: local (per project) and global (for the user's whole machine). In both modes, the main agent `sdd-orchestrator` is automatically renamed to `ospec-workflow` to integrate with the OpenCode interface and allow Tab-key autocomplete.

#### Local installation (per project)

Build and sync the plugin folder directly into the root of your destination project:

```powershell
npm run install:opencode -- ../my-project
```

This will copy the `.opencode/` tree, `opencode.json`, `skills/`, and `scripts/` (including the hook scripts and the compiler hook binary `ospec-hooks.exe` or `ospec-hooks` if it was compiled into `release/dist/`).

#### Global installation (for any project)

Install the plugin permanently at user level:

```powershell
npm run setup:opencode
```

*(If you make modifications and need to update the global installation, you can rerun `npm run reload:opencode` or `npm run setup:opencode` interchangeably).*

This idempotent installer performs the following steps:
1. Builds the `opencode` target into `dist/opencode/`.
2. Copies the compiler hook binary `ospec-hooks` appropriate for the architecture into `release/dist/` (if present).
3. Copies all generated folders (`agents/`, `commands/`, `instructions/`, `plugins/`, `skills/`, `scripts/`, and `release/`) to the global OpenCode configuration directory:
   - **Windows**: `C:\Users\<User>\.config\opencode\`
   - **Linux/macOS**: `~/.config/opencode/`
4. Dynamically merges the configurations from `opencode.json` (including MCP servers such as `context7` and `markitdown`) with the existing global `opencode.json`, and adds the global pattern `instructions/*.md` to register the instructions.

The plugin resolves `ospec-hooks` first from `release/dist/` next to the global installation, then from the project's local layout, and only as a last resort from `PATH`. There is no need to add the binary directory to `PATH` for a managed installation.

This makes `ospec-workflow` and all its commands/skills available by pressing **Tab** in any repository opened in OpenCode.

### Cursor IDE

The `cursor` target installs natively into the global Cursor home (`~/.cursor`). There is no repo-local `.cursor/` installation in this change.

```powershell
npm run build:cursor
npm run setup:cursor
```

*(To update, run `npm run setup:cursor` or `npm run reload:cursor` again.)*

This idempotent installer:
1. Builds and validates `dist/cursor/` with `runConfigure({ target: "cursor", validate: true })`.
2. Applies `assertCursorPathSafe` over `~/.cursor` (allows `$HOME/.cursor`; rejects the FS root, symlinks, and canonical escapes).
3. Syncs the generated tree by content comparison (preserves unrelated user files).
4. Writes `hooks.json` with `__OSPEC_CURSOR_ROOT__` already expanded to the absolute path in POSIX slashes (quoted only if the path has spaces).
5. Copies the `ospec-hooks` binary to `~/.cursor/scripts/hooks/` when it exists in `release/dist/`.
6. `--dry-run` validates and writes nothing under `~/.cursor`.

## Troubleshooting

| Symptom | Likely cause | What to check |
| --- | --- | --- |
| Agent Plugins UI missing | The Agent Plugins preview is unavailable or policy disables it. | Confirm your VS Code version supports Agent Plugins and review your organization's policy. |
| The plugin does not appear from `chat.pluginLocations` | The path points to the wrong folder or VS Code has not been reloaded. | Point to the repository root containing `.plugin.json` and then reload VS Code. |
| Prompt files missing | The plugin is disabled or the prompt assets were not loaded. | Confirm `.plugin.json` references `commands/` and that the plugin is enabled. |
| `sdd-orchestrator` missing | The agent assets were not loaded. | Confirm `.plugin.json` references `agents/` and that the Agent Plugins view shows no errors. |
| Skills seem unavailable | The skill assets were not loaded or the request did not trigger a skill. | Confirm `.plugin.json` references `skills/` and try again with an SDD request. |
| MCP server missing | MCP is disabled, blocked by policy, or unavailable in the current version. | Check the MCP/tools settings, the organization policy, Node.js/`npx` (Context7), and `uv`/`uvx` (MarkItDown). |
| Context7 asks for a key | `CONTEXT7_API_KEY` is missing. | Provide it from the VS Code prompt when trusting server execution. |
| Hook execution fails | Problem with Node.js, path resolution, or script policy. | Confirm Node.js is on `PATH`, review `hooks/hooks.json`, the resolution of `${PLUGIN_ROOT}`, and the scripts in `scripts/hooks/`. |
| Hooks must not run | Local code execution is not allowed in this environment. | Disable the plugin or use a local copy without hooks. |

## Versioning policy

Treat the plugin manifest version as the installed package version.

| Change type | Version guidance | Examples |
| --- | --- | --- |
| Patch | Fixes or docs that do not change plugin behavior. | Clarify installation, fix typos, improve troubleshooting. |
| Minor | Backward-compatible plugin capability changes. | Adding a command, adding a skill, adding a new hook with safe default values, updating MCP configuration without breaking existing usage. |
| Major | Changes that break behavior or the trust surface. | Renaming commands, removing agents, changing required MCP inputs, replacing hook behavior, or changing SDD phase contracts incompatibly. |

Update flow for users who already installed:

1. Review the changelog or the diff before updating, especially if `.plugin.json`, `.claude-plugin/plugin.json`, `.mcp.json`, `hooks/hooks.json`, or `scripts/hooks/` changed.
2. Pull or reinstall from the Git repository URL.
3. Reload VS Code.
4. Re-run the agent, command, MCP, and hook checks in this document.

When a release changes hooks or MCP servers, state it explicitly because it changes the local execution and trust surface.
